- Подтверждена архитектура: одна коллекция Chroma `knowledge_base` хранит несколько логических баз знаний, разделённых по metadata-полю `themeId` (мультитенантность через фильтрацию, без отдельных коллекций на тему).
- **`backend/rag/vectorStore.js`**:
  - `searchChunks` теперь требует обязательный `filters.themeId` (бросает ошибку при отсутствии) — закрыт риск поиска по всей коллекции сразу по всем темам при забытом фильтре.
  - `deleteByThemeId` требует обязательный `themeId`; удаление переведено с `get({where})` + `delete({ids})` на прямой `delete({ where: { themeId } })` (без промежуточной выгрузки id в память), количество удалённых записей считается через `collection.count()` до/после.
- **`backend/server.js`**:
  - `POST /api/pdf/upload`: `themeId` валидируется против списка тем в `themeCollection.json`, иначе 400.

- **`backend/test-rag-flow.js`**: тестовый вызов `searchChunks` обновлён — передаёт `themeId: 'test-theme'`.

**Затронутые пути:**
- `backend/rag/vectorStore.js`
- `backend/server.js`
- `backend/test-rag-flow.js`

**Зачем / контекст:** Единая коллекция ChromaDB с фильтрацией по `themeId` — рабочий паттерн для нескольких баз знаний в одном хранилище. Единственный риск такого подхода — забытый фильтр в вызывающем коде приводит к утечке чанков между темами; правки делают `themeId` обязательным на уровне API и векторного хранилища, устраняя эту дыру.

## 2026-07-22 — Единообразие разделов PDF при обработке

**Область:** Backend, RAG

**Что изменилось:**
- **`backend/rag/pdfParser.js`**: Функция `extractSections` теперь принимает третий опциональный параметр `sectionTitles` (массив строк). Если передан — текст режется по этим заголовкам без повторного regex-сканирования.
  - При `processPdf === 'true'` используется `result.sections` из `cleanPdf()` — те же заголовки, что администратор видел при тестировании regex.
  - Если `sectionTitles` не передан — работает старый встроенный regex (обратная совместимость).
- **`backend/server.js` (эндпоинт `/api/pdf/upload`)**:
  - При включённой обработке PDF (`processPdf === 'true'`) в `extractSections` передаются готовые заголовки из `cleanedSections` вместо повторного regex-сканирования.
  - Разделы для чанкинга и RAG гарантированно совпадают с теми, что отображаются в блоке «Доступные разделы в источнике (очистка)».

**Зачем / контекст:**
Предыдущий подход всё ещё мог давать расхождения из-за разного нормализованного формата строк (regex vs raw-текст). Теперь разделы — это один и тот же массив строк на всём конвейере: тест regex → очистка → индексация → семантический поиск → страница «Маршрут обучения».

## 2026-07-16 — Исправление Mixed Content на VDS (HTTPS/HTTP)

**Область:** Frontend, Infrastructure, Networking

**Что изменилось:**
- **`src/lib/apiBase.ts`**: Переработана логика `getPublicApiBaseUrl()`:
  - На серверной стороне (Next.js API Routes) — использует `NEXT_PUBLIC_API_BASE_URL` или дефолт `http://localhost:3031`.
  - В браузере на `localhost` — прямой доступ к бэкенду (`http://localhost:3031`) для разработки.
  - В браузере на проде — возвращает `""` (относительный URL = same-origin), чтобы запросы шли через HTTPS на тот же домен.
- **`next.config.mjs`**: Добавлены rewrite-правила для `/api/pdf/:path*` и `/api/admin/:path*`, чтобы клиентские запросы к этим эндпоинтам проксировались через Next.js-сервер внутри Docker-сети.

**Зачем / контекст:**
На VDS страница загружается по HTTPS, но клиентские компоненты (`knowledgeJourney`, `admin/sources`, `successJournal`, `TimerFreeResponse`) вызывали `getPublicApiBaseUrl()`, которая возвращала `http://backend:3031`. Браузер блокировал HTTP-запросы с HTTPS-страницы (Mixed Content). Теперь все клиентские запросы идут через same-origin → Next.js proxy → бэкенд.

## 2026-07-23 — Исправление ChromaDB ChromaValueError при нескольких фильтрах

**Область:** Backend, RAG

**Что изменилось:**
- **`backend/rag/vectorStore.js` (`searchChunks`)**: при нескольких фильтрах (`pdfId`, `sectionTitle`, `themeId`) объект `where` собирался как `{ pdfId, sectionTitle, themeId }` — ChromaDB требует ровно один оператор на верхнем уровне `where` и падал с `ChromaValueError: Expected 'where' to have exactly one operator, but got 3`.
- Теперь условия собираются в массив и, если их больше одного, оборачиваются в `{ $and: [...] }`; при одном условии передаётся как есть; при отсутствии — `where` не передаётся.

**Зачем / контекст:**
Баг проявился после унификации RAG-фильтра (см. запись ниже) — генерация тестов с включённым RAG падала при выборе PDF+раздела.

## 2026-07-23 — Приведение RAG-условий к единому виду в эндпоинтах генерации

**Область:** Backend

**Что изменилось:**

  - Вместо `if (themeId && gigachatClient)` (GigaChat) и `if (pdfId && gigachatClient)` (YandexGPT) — теперь везде `if (pdfId && gigachatClient)`.
  - Из фильтра поиска `searchChunks()` убран `themeId` — при выбранном PDF достаточно `pdfId` для точной фильтрации.

**Зачем / контекст:**
Была неконсистентность: GigaChat пытался искать в ChromaDB даже без выбранного PDF (только по `themeId`), что могло возвращать чанки от любого PDF темы. Теперь RAG включается только когда фронтенд явно передал `pdfId`.

  - `join('\\n')` → `join('\n')` — правильная склейка с переводами строк
  - `join('\\n---\\n')` → `join('\n---\n')` — для контекста RAG
  - Шаблонные строки `` `\\n\\nКонтекст...` `` → `` `\n\nКонтекст...` ``
- **Причина**: Из-за двойного экранирования (`\\n` в коде = литерал `\n`) `split` не находил реальные
  переводы строк в systemPrompt. Весь systemPrompt заменялся на один topicPrompt,
  AI не получал инструкций про JSON-формат `journey` и не генерировал тесты.
- Рабочая версия (`main.js` из другой ветки) использовала одинарное экранирование `\n`.

**Зачем / контекст:**
Ошибка 413 (Request Entity Too Large) возникала из-за дефолтного лимита Nginx в 1MB. Ошибка 504 (Gateway Time-out) — из-за дефолтного таймаута Nginx в 60 секунд, которого не хватало на индексацию PDF (парсинг, чанкинг, эмбеддинги через GigaChat API).
